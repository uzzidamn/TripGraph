## Unspecified Decisions Made During Build

### Docker healthcheck uses wget instead of `neo4j status`
The spec suggested `neo4j status || exit 1` as the healthcheck command. The neo4j:5-community
image uses Java-based startup and `neo4j status` may not be available in the slim image PATH.
Used `wget -q --spider http://localhost:7474` instead — checks the HTTP browser port which is
reliably up when Neo4j is ready. Added `start_period: 30s` to give Neo4j time to initialize.

### Workflow import is lazy (inside try block, not at module top)
`from backend.agents.workflow import run_workflow` is inside the route function body, not at
module import time. This lets the FastAPI app start and serve /health even if the agents
package has an import error (e.g. missing GOOGLE_API_KEY). Routes fail gracefully at call
time rather than crashing the whole server at startup.

### _constraints_to_chat uses full natural language sentences
The spec said to implement `_constraints_to_chat()` as a helper. Made the synthetic sentences
more verbose than a minimal approach ("We want to travel from Gurugram" rather than "origin:
Gurugram") so the Chat Parser LLM can reliably extract the constraint in the same way it would
from real group chat.

### SimulateDelay changes extraction from replanned_itinerary
The spec's response schema has `changes` as a top-level field in DelaySimulationResponse.
The replanner stores changes inside the `updated_itinerary` dict under the `changes` key.
Added `replanned.pop("changes", [])` to lift the changes list out before returning the dict
as updated_itinerary.

### No .env.example created
The spec explicitly says: "Note: .env.example already exists in the repo root. Do NOT create
a new one." Confirmed — not created.

## Deviations from Spec

### Decision 5: HTTP 503 for Neo4j unreachable
The spec says return HTTP 503 for Neo4j connection failures. Not implemented as a distinct
case — Neo4j failures surface as generic HTTP 500 from the workflow exception. Reason: the
pipeline's data_retriever already falls back to mock data when Neo4j is offline (Bucket 2
decision), so a true "503 no database" scenario rarely occurs. The 503 distinction can be
added later by inspecting the exception type.
